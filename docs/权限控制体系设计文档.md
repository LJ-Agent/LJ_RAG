# RAG 权限控制体系设计文档

> 目标：建立「团队 → 成员角色 → 知识库」三级权限模型，实现团队间资源隔离和团队内角色分工。

---

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                    系统级权限 (Global)                     │
│  超级管理员: USER:*, CONFIG:MANAGE, 跨团队数据访问         │
├──────────────────────────────────────────────────────────┤
│  团队A                    │  团队B                       │
│  ┌──────────────────┐    │  ┌──────────────────┐        │
│  │ 团队所有者 (1人)  │    │  │ 团队所有者 (1人)  │        │
│  │ 团队管理员 (N人)  │    │  │ 团队管理员 (N人)  │        │
│  │ 编辑者     (N人)  │    │  │ 编辑者     (N人)  │        │
│  │ 审核者     (N人)  │    │  │ 审核者     (N人)  │        │
│  │ 访客       (N人)  │    │  │ 访客       (N人)  │        │
│  └──────────────────┘    │  └──────────────────┘        │
│  ├─ KB1 (创业知识库)      │  ├─ KB3 (技术文档库)          │
│  ├─ KB2 (产品手册)        │  └─ KB4 (运维手册)            │
│  └─ ...                  │                             │
├──────────────────────────┴──────────────────────────────┤
│  权限生效规则: 用户只能看到其所属团队关联的知识库           │
│  角色权限取最高值 (一个用户可在不同团队有不同角色)          │
└──────────────────────────────────────────────────────────┘
```

## 2. 数据模型

### 2.1 核心表

```sql
-- ==================== 团队 ====================
CREATE TABLE teams (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(128) NOT NULL COMMENT '团队名称',
    description VARCHAR(512) COMMENT '团队描述',
    owner_id    BIGINT NOT NULL COMMENT '创建者(团队所有者)',
    status      TINYINT DEFAULT 1 COMMENT '1=启用 0=禁用',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_owner (owner_id)
) COMMENT='团队';

-- ==================== 团队成员 ====================
CREATE TABLE team_members (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    team_id     BIGINT NOT NULL COMMENT '团队ID',
    user_id     BIGINT NOT NULL COMMENT '用户ID',
    role_code   VARCHAR(32) NOT NULL COMMENT '团队角色: team_owner/team_admin/team_editor/team_reviewer/team_viewer',
    joined_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    invited_by  BIGINT COMMENT '邀请人ID',
    UNIQUE KEY uk_team_user (team_id, user_id),
    INDEX idx_user (user_id),
    INDEX idx_team (team_id)
) COMMENT='团队成员及角色';

-- ==================== 团队知识库关联 ====================
CREATE TABLE team_knowledge_bases (
    id      BIGINT AUTO_INCREMENT PRIMARY KEY,
    team_id BIGINT NOT NULL COMMENT '团队ID',
    kb_id   BIGINT NOT NULL COMMENT '知识库ID',
    UNIQUE KEY uk_team_kb (team_id, kb_id),
    INDEX idx_kb (kb_id)
) COMMENT='团队与知识库关联';
```

### 2.2 扩展现有表

```sql
-- knowledge_bases 表新增 team_id (可选，null=全局可见/个人知识库)
ALTER TABLE knowledge_bases ADD COLUMN team_id BIGINT COMMENT '归属团队ID';
ALTER TABLE knowledge_bases ADD COLUMN visibility VARCHAR(16) DEFAULT 'team' COMMENT 'team=团队内可见 public=全员可见 private=仅自己';
```

### 2.3 关系示意

```
teams (1) ──< (N) team_members (N) >── (1) users
  │
  │ (1)
  ├──< (N) team_knowledge_bases (N) >── (1) knowledge_bases
  │
  └── team_members.role_code 决定用户在团队内的权限
```

## 3. 团队角色定义

| 角色 | role_code | 权限范围 | 典型权限 |
|------|-----------|----------|----------|
| 团队所有者 | `team_owner` | 团队全部资源 | 管理成员、删除团队、全部文档操作 |
| 团队管理员 | `team_admin` | 团队全部资源 | 管理成员(除owner)、全部文档操作 |
| 编辑者 | `team_editor` | 团队知识库 | 上传/编辑文档、发起问答 |
| 审核者 | `team_reviewer` | 团队知识库 | 审核文档、查看文档 |
| 访客 | `team_viewer` | 团队知识库 | 只读查看、问答 |

| 创建/删除知识库 | ✅ | ✅ | ❌ | ❌ | ❌ |

## 4. 权限控制流程

### 4.1 知识库列表查询

```
用户请求 GET /api/knowledge-bases
  ↓
1. 查询用户所属所有团队: SELECT team_id FROM team_members WHERE user_id = ?
2. 查询这些团队关联的知识库: SELECT kb_id FROM team_knowledge_bases WHERE team_id IN (...)
3. 加上 visibility='public' 的知识库
4. 返回交集结果
```

### 4.2 上传文档

```
POST /api/files/upload { kbId: 5, ... }
  ↓
1. 查询 kbId=5 归属的 team_id
2. 查询用户在 team_id 中的角色
3. 检查角色是否有 DOCUMENT:UPLOAD 权限
4. 有权限 → 执行上传 | 无权限 → 403
```

### 4.3 系统级管理员 (跨团队)

```
超级管理员 (拥有 GLOBAL:ADMIN 权限)
  ↓
跳过团队隔离检查 → 可查看所有知识库和文档
系统配置 (CONFIG:MANAGE) → 仅超级管理员可访问
```

## 5. API 设计

### 5.1 团队管理 (管理员)

```
POST   /api/teams                       创建团队
GET    /api/teams                       我的团队列表
GET    /api/teams/{id}                  团队详情
PUT    /api/teams/{id}                  编辑团队

POST   /api/teams/{id}/members          邀请成员
DELETE /api/teams/{id}/members/{userId} 移除成员
PUT    /api/teams/{id}/members/{userId} 修改成员角色
GET    /api/teams/{id}/members          成员列表
POST   /api/teams/{id}/kbs/{kbId}       关联知识库
DELETE /api/teams/{id}/kbs/{kbId}       取消关联
```

### 5.2 知识库 (增强)

```
GET /api/knowledge-bases?teamId={id}   按团队筛选 (自动按用户所属团队过滤)
```

### 5.3 权限检查注解

```java
// 新增自定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface TeamPermission {
    String value();  // 所需权限码, 如 "DOCUMENT:UPLOAD"
}

// 使用示例
@TeamPermission("DOCUMENT:UPLOAD")
@PostMapping("/upload")
public Result<FileVO> upload(...) { }

// AOP切面自动获取 kbId → 查询团队 → 校验角色权限
```

## 6. 与现有权限体系的兼容

| 现有概念 | 改动 |
|----------|------|
| `users` 表 | 不变 |
| `roles` 表 | 保留作为「系统级角色」(admin/reviewer/editor/viewer) |
| `permissions` 表 | 保留，18个权限码不变 |
| `knowledge_bases` | 新增 `team_id` 和 `visibility` 字段 |
| JWT Token | 新增 `teams: [{teamId, role}]` 字段 |

### 系统角色 → 团队角色映射

```
系统角色 admin    → 所有团队视为 team_admin (跨团队)
系统角色 reviewer → 所属团队内为 team_reviewer
系统角色 editor   → 所属团队内为 team_editor
系统角色 viewer   → 所属团队内为 team_viewer
```

## 8. API 层面越权防护

### 8.1 垂直越权防护

> 低权限用户访问高权限 API

```java
// 方案1: Spring Security @PreAuthorize (方法级)
@PreAuthorize("hasAuthority('CONFIG:MANAGE')")   // 仅管理员
@GetMapping("/api/configs")
public Result<...> systemConfigs() { }

@PreAuthorize("hasAnyAuthority('DOCUMENT:UPLOAD','KB:CREATE')")  // 上传/创建权限
@PostMapping("/api/files/upload")
public Result<...> upload() { }

// 方案2: AOP 自定义注解 (声明式)
@TeamPermission(value = "USER:DELETE", resourceType = ResourceType.KB)
@DeleteMapping("/api/users/{id}")
public Result<...> deleteUser() { }
```

**防护矩阵**：

| 用户角色 | 尝试访问 | 机制 | 结果 |
|----------|----------|------|------|
| viewer | `/api/configs` | `@PreAuthorize("CONFIG:MANAGE")` | 403 垂直拦截 |
| editor | `/api/users/{id}` DELETE | `@PreAuthorize("USER:DELETE")` | 403 垂直拦截 |
| viewer | `/api/files/upload` | `@PreAuthorize("DOCUMENT:UPLOAD")` | 403 垂直拦截 |

### 8.2 水平越权防护

> 同权限级别用户访问其他团队/用户资源

```java
// AOP 自动校验：用户 ∈ KB的团队
@TeamPermission(value = "DOCUMENT:VIEW", resourceType = ResourceType.DOCUMENT)
@GetMapping("/api/files/{id}/content")
public void getContent(@PathVariable Long id) { }

// 执行流程:
// 1. 提取 id=123 → 查询 document.findById(123) → kbId=5
// 2. 查询 kbId=5 → 查询 team_knowledge_bases → teamId=2
// 3. 查询 team_members WHERE user_id=? AND team_id=2
// 4. 存在记录 → 放行 | 不存在 → 403 水平拦截
```

**防护矩阵**：

| 用户 | 尝试访问 | 归属 | 机制 | 结果 |
|------|----------|------|------|------|
| bob(teamA) | `/api/files/123/content` (doc在teamA) | bob∈teamA | AOP团队匹配 | 200 放行 |
| bob(teamA) | `/api/files/456/content` (doc在teamB) | bob∉teamB | AOP团队不匹配 | 403 水平拦截 |
| bob(teamA) | `POST /api/files/upload?kbId=7` (KB在teamB) | bob∉teamB | AOP团队不匹配 | 403 水平拦截 |

### 8.3 具体 API 防护清单

```java
@RestController @RequestMapping("/api/files")
public class FileController {

    // 垂直: DOCUMENT:UPLOAD | 水平: kbId 归属团队
    @TeamPermission(value = "DOCUMENT:UPLOAD", resourceType = ResourceType.KB)
    @PostMapping("/upload")
    public Result<FileVO> upload(@RequestParam Long kbId, ...) { }

    // 垂直: DOCUMENT:VIEW | 水平: id→document→kbId→team
    @TeamPermission(value = "DOCUMENT:VIEW", resourceType = ResourceType.DOCUMENT)
    @GetMapping("/{id}")
    public Result<FileVO> detail(@PathVariable Long id) { }

    // 垂直: DOCUMENT:DELETE | 水平: id→kbId→team
    @TeamPermission(value = "DOCUMENT:DELETE", resourceType = ResourceType.DOCUMENT)
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) { }

    // 垂直: DOCUMENT:VIEW | 水平: id→kbId→team
    @TeamPermission(value = "DOCUMENT:VIEW", resourceType = ResourceType.DOCUMENT)
    @GetMapping("/{id}/content")
    public void getContent(@PathVariable Long id, ...) { }
}

@RestController @RequestMapping("/api/knowledge-bases")
public class KnowledgeBaseController {

    // 团队列表已过滤 → 不需要水平校验
    @GetMapping
    public Result<...> list() { }  // Service层按teams过滤

    // 垂直: KB:DELETE | 水平: kbId→team
    @TeamPermission(value = "KB:DELETE", resourceType = ResourceType.KB)
    @DeleteMapping("/{id}")
    public Result<Void> delete(@PathVariable Long id) { }
}
```

### 8.4 双层校验体系

```
HTTP Request
  ↓
[Filter] JwtAuthenticationFilter → 解析Token → 设置SecurityContext
  ↓
[Spring Security] 检查 anyRequest().authenticated()
  ↓
[AOP @PreAuthorize] 检查方法级权限码 (垂直越权)
  ↓
[AOP @TeamPermission] 检查资源归属团队 (水平越权)
  ↓
[Service] 业务逻辑执行
  ↓
Response
```

**关键原则**：
1. 垂直越权靠 `@PreAuthorize` 拦截 — API网关层
2. 水平越权靠 `@TeamPermission` AOP 拦截 — 资源归属层
3. Service 层不做权限判断，专注业务逻辑
4. 超级管理员 (CONFIG:MANAGE) 跳过团队检查

## 9. 数据隔离示例

```
团队「AI研发组」成员: alice(owner), bob(editor), charlie(viewer)
团队「数据平台组」成员: david(owner), bob(editor)

bob 在两个团队都是 editor → 能看到两个团队的知识库
  ├── AI研发组: KB-A, KB-B
  └── 数据平台组: KB-C

charlie 只在 AI研发组是 viewer → 只能看到 KB-A, KB-B (只读)

alice (owner) 可以邀请新成员、删除 KB-A
bob 不能删除 KB-A (非owner), 但可以上传文档到 KB-A
```

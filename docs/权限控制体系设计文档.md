# RAG 权限控制体系设计文档

> 目标：建立「团队 → 成员角色 → 知识库」三级权限模型，实现团队间资源隔离和团队内角色分工。

---

## 1. 总体架构

```
┌──────────────────────────────────────────────────────────┐
│                    系统级权限 (Global)                     │
│  超级管理员: USER:*, CONFIG:MANAGE, 跨团队数据访问         │
├──────────────────────────────────────────────────────────┤
│  团队A                    │  团队B                       │
│  ┌──────────────────┐    │  ┌──────────────────┐        │
│  │ 团队所有者 (1人)  │    │  │ 团队所有者 (1人)  │        │
│  │ 团队管理员 (N人)  │    │  │ 团队管理员 (N人)  │        │
│  │ 编辑者     (N人)  │    │  │ 编辑者     (N人)  │        │
│  │ 审核者     (N人)  │    │  │ 审核者     (N人)  │        │
│  │ 访客       (N人)  │    │  │ 访客       (N人)  │        │
│  └──────────────────┘    │  └──────────────────┘        │
│  ├─ KB1 (创业知识库)      │  ├─ KB3 (技术文档库)          │
│  ├─ KB2 (产品手册)        │  └─ KB4 (运维手册)            │
│  └─ ...                  │                             │
├──────────────────────────┴──────────────────────────────┤
│  权限生效规则: 用户只能看到其所属团队关联的知识库           │
│  角色权限取最高值 (一个用户可在不同团队有不同角色)          │
└──────────────────────────────────────────────────────────┘
```

## 2. 数据模型

### 2.1 核心表

```sql
-- ==================== 团队 ====================
CREATE TABLE teams (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    name        VARCHAR(128) NOT NULL COMMENT '团队名称',
    description VARCHAR(512) COMMENT '团队描述',
    owner_id    BIGINT NOT NULL COMMENT '创建者(团队所有者)',
    status      TINYINT DEFAULT 1 COMMENT '1=启用 0=禁用',
    created_at  DATETIME DEFAULT CURRENT_TIMESTAMP,
    updated_at  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    INDEX idx_owner (owner_id)
) COMMENT='团队';

-- ==================== 团队成员 ====================
CREATE TABLE team_members (
    id          BIGINT AUTO_INCREMENT PRIMARY KEY,
    team_id     BIGINT NOT NULL COMMENT '团队ID',
    user_id     BIGINT NOT NULL COMMENT '用户ID',
    role_code   VARCHAR(32) NOT NULL COMMENT '团队角色: team_owner/team_admin/team_editor/team_reviewer/team_viewer',
    joined_at   DATETIME DEFAULT CURRENT_TIMESTAMP,
    invited_by  BIGINT COMMENT '邀请人ID',
    UNIQUE KEY uk_team_user (team_id, user_id),
    INDEX idx_user (user_id),
    INDEX idx_team (team_id)
) COMMENT='团队成员及角色';

-- ==================== 团队知识库关联 ====================
CREATE TABLE team_knowledge_bases (
    id      BIGINT AUTO_INCREMENT PRIMARY KEY,
    team_id BIGINT NOT NULL COMMENT '团队ID',
    kb_id   BIGINT NOT NULL COMMENT '知识库ID',
    UNIQUE KEY uk_team_kb (team_id, kb_id),
    INDEX idx_kb (kb_id)
) COMMENT='团队与知识库关联';
```

### 2.2 扩展现有表

```sql
-- knowledge_bases 表新增 team_id (可选，null=全局可见/个人知识库)
ALTER TABLE knowledge_bases ADD COLUMN team_id BIGINT COMMENT '归属团队ID';
ALTER TABLE knowledge_bases ADD COLUMN visibility VARCHAR(16) DEFAULT 'team' COMMENT 'team=团队内可见 public=全员可见 private=仅自己';
```

### 2.3 关系示意

```
teams (1) ──< (N) team_members (N) >── (1) users
  │
  │ (1)
  ├──< (N) team_knowledge_bases (N) >── (1) knowledge_bases
  │
  └── team_members.role_code 决定用户在团队内的权限
```

## 3. 团队角色定义

| 角色 | role_code | 权限范围 | 典型权限 |
|------|-----------|----------|----------|
| 团队所有者 | `team_owner` | 团队全部资源 | 管理成员、删除团队、全部文档操作 |
| 团队管理员 | `team_admin` | 团队全部资源 | 管理成员(除owner)、全部文档操作 |
| 编辑者 | `team_editor` | 团队知识库 | 上传/编辑文档、发起问答 |
| 审核者 | `team_reviewer` | 团队知识库 | 审核文档、查看文档 |
| 访客 | `team_viewer` | 团队知识库 | 只读查看、问答 |

| 权限 | team_owner | team_admin | team_editor | team_reviewer | team_viewer |

| 删除团队 | ✅ | ❌ | ❌ | ❌ | ❌ |
| 创建/删除知识库 | ✅ | ✅ | ❌ | ❌ | ❌ |
| 上传文档 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 编辑文档信息 | ✅ | ✅ | ✅ | ❌ | ❌ |
| 删除文档 | ✅ | ✅ | ✅(自己上传) | ❌ | ❌ |
| 审核文档 | ✅ | ✅ | ❌ | ✅ | ❌ |

## 4. 权限控制流程

### 4.1 知识库列表查询

```
用户请求 GET /api/knowledge-bases
  ↓
1. 查询用户所属所有团队: SELECT team_id FROM team_members WHERE user_id = ?
2. 查询这些团队关联的知识库: SELECT kb_id FROM team_knowledge_bases WHERE team_id IN (...)
3. 加上 visibility='public' 的知识库
4. 返回交集结果
```

### 4.2 上传文档

```
POST /api/files/upload { kbId: 5, ... }
  ↓
1. 查询 kbId=5 归属的 team_id
2. 查询用户在 team_id 中的角色
3. 检查角色是否有 DOCUMENT:UPLOAD 权限
4. 有权限 → 执行上传 | 无权限 → 403
```

### 4.3 系统级管理员 (跨团队)

```
超级管理员 (拥有 GLOBAL:ADMIN 权限)
  ↓
跳过团队隔离检查 → 可查看所有知识库和文档
系统配置 (CONFIG:MANAGE) → 仅超级管理员可访问
```

## 5. API 设计

### 5.1 团队管理 (管理员)

```
POST   /api/teams                       创建团队
GET    /api/teams                       我的团队列表
GET    /api/teams/{id}                  团队详情
PUT    /api/teams/{id}                  编辑团队
DELETE /api/teams/{id}                  删除团队 (仅owner)
POST   /api/teams/{id}/members          邀请成员
DELETE /api/teams/{id}/members/{userId} 移除成员
PUT    /api/teams/{id}/members/{userId} 修改成员角色
GET    /api/teams/{id}/members          成员列表
POST   /api/teams/{id}/kbs/{kbId}       关联知识库
DELETE /api/teams/{id}/kbs/{kbId}       取消关联
```

### 5.2 知识库 (增强)

```
GET /api/knowledge-bases?teamId={id}   按团队筛选 (自动按用户所属团队过滤)
```

### 5.3 权限检查注解

```java
// 新增自定义注解
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface TeamPermission {
    String value();  // 所需权限码, 如 "DOCUMENT:UPLOAD"
}

// 使用示例
@TeamPermission("DOCUMENT:UPLOAD")
@PostMapping("/upload")
public Result<FileVO> upload(...) { }

// AOP切面自动获取 kbId → 查询团队 → 校验角色权限
```

## 6. 与现有权限体系的兼容

| 现有概念 | 改动 |
|----------|------|
| `users` 表 | 不变 |
| `roles` 表 | 保留作为「系统级角色」(admin/reviewer/editor/viewer) |
| `permissions` 表 | 保留，18个权限码不变 |
| `knowledge_bases` | 新增 `team_id` 和 `visibility` 字段 |
| JWT Token | 新增 `teams: [{teamId, role}]` 字段 |

### 系统角色 → 团队角色映射

```
系统角色 admin    → 所有团队视为 team_admin (跨团队)
系统角色 reviewer → 所属团队内为 team_reviewer
系统角色 editor   → 所属团队内为 team_editor
系统角色 viewer   → 所属团队内为 team_viewer
```

## 8. 数据隔离示例

```
团队「AI研发组」成员: alice(owner), bob(editor), charlie(viewer)
团队「数据平台组」成员: david(owner), bob(editor)

bob 在两个团队都是 editor → 能看到两个团队的知识库
  ├── AI研发组: KB-A, KB-B
  └── 数据平台组: KB-C

charlie 只在 AI研发组是 viewer → 只能看到 KB-A, KB-B (只读)

alice (owner) 可以邀请新成员、删除 KB-A
bob 不能删除 KB-A (非owner), 但可以上传文档到 KB-A
```

### 2.1 设计原理

RAG-BACKEND 通过 **三个机制** 实现单体和微服务的无缝切换，**零代码重复，零运行时切换代价**。

#### 机制一：Maven 多模块依赖

```
rag-common/         ← 共享层 (Entity/Mapper/Infra/Common)
    ↑               ↑        ↑        ↑        ↑
rag-auth    rag-kb    rag-doc    rag-qa    rag-config
    ↓         ↓        ↓         ↓         ↓
rag-monolith/       ← 聚合所有模块 → 单体 JAR
```

```xml
<!-- rag-monolith/pom.xml: 依赖全部模块 -->
<dependencies>
    <dependency>rag-common</dependency>
    <dependency>rag-auth</dependency>
    <dependency>rag-kb</dependency>
    <dependency>rag-doc</dependency>
    <dependency>rag-qa</dependency>
    <dependency>rag-config</dependency>
</dependencies>

<!-- rag-auth/pom.xml: 只依赖共享层 -->
<dependencies>
    <dependency>rag-common</dependency>
</dependencies>
```

**构建**：
```bash
# 单体：拉取所有模块打成单体 JAR
mvn package -pl rag-monolith -am

# 微服务：只打包该模块 + 它依赖的 rag-common
mvn package -pl rag-auth -am
mvn package -pl rag-kb -am
```

#### 机制二：Spring Profile 控制 Bean 加载

13 个 Controller 全部标注 `@Profile`，同一个类在单体和微服务模式下的加载规则不同：

```java
// AuthController.java
@Profile({"auth", "prod"})   // prod=单体也加载, auth=微服务才加载
@RestController
public class AuthController { ... }

// FileController.java
@Profile({"doc", "prod"})
@RestController
public class FileController { ... }
```

| 启动参数 | 匹配规则 | 加载结果 |
|------|------|------|
| `SPRING_PROFILES_ACTIVE=prod` | 全部 `@Profile({..., "prod"})` 匹配 | 13个Controller全部加载 → 单体 |
| `SPRING_PROFILES_ACTIVE=auth` | 只有 `@Profile({"auth","prod"})` 匹配 | 仅Auth/User/Role/Permission → 微服务 |
| `SPRING_PROFILES_ACTIVE=kb` | 只有 `@Profile({"kb","prod"})` 匹配 | 仅KB/Team → 微服务 |

#### 机制三：各自独立的 Main 类

```java
// rag-monolith 启动类 → Profile=prod, 全量加载
@SpringBootApplication
public class RagApplication {
    public static void main(String[] args) {
        SpringApplication.run(RagApplication.class, args);
    }
}

// rag-auth 启动类 → Profile=auth, 只加载认证相关Bean
@SpringBootApplication
public class RagAuthApplication {
    public static void main(String[] args) {
        SpringApplication.run(RagAuthApplication.class, args);
    }
}
```

#### 三个机制协作全景

```
同一份 Controller 代码
    │
    ├── Maven 机制: rag-monolith依赖全部 → 单体JAR
    │              rag-auth只依赖common → 微服务JAR
    │
    ├── Profile 机制: SPRING_PROFILES_ACTIVE=prod → 全部@Profile匹配 → 13个Controller加载
    │                 SPRING_PROFILES_ACTIVE=auth → 仅auth的@Profile匹配 → 4个Controller加载
    │
    └── Main 类机制: RagApplication(monolith) → 单体入口
                     RagAuthApplication(auth)  → 微服务入口

零重复代码，单体和微服务的区别 = Maven参数 + Profile参数 + Main类
```

```java
// AuthController.java — 同时支持单体和微服务
@Profile({"auth", "prod"})  // prod=单体加载, auth=微服务auth模块加载
@RestController
public class AuthController { ... }
```

- **SPRING_PROFILES_ACTIVE=prod**：匹配所有 `@Profile({..., "prod"})` → 单体模式
- **SPRING_PROFILES_ACTIVE=auth**：仅匹配 `@Profile({"auth", "prod"})` → 微服务auth模块

### 2.2 两种模式对比

| 维度 | 单体模式 | 微服务模式 |
|------|----------|------------|
| 构建命令 | `mvn package` | `mvn package -pl rag-auth -am` |
| 容器数 | 1 个 (rag-server) | 5 个 (rag-auth/kb/doc/qa/config) |
| 内存 | ~700MB | ~700MB × 5 |
| 端口 | :8080 | :8081~:8085 |
| Profile | `prod` | `auth`/`kb`/`doc`/`qa`/`config` |
| 故障隔离 | ❌ 单点 | ✅ 独立 |
| 独立扩缩 | ❌ | ✅ |
| 部署复杂度 | 低 | 中 |
| 当前状态 | ✅ 已验证 | ⏳ 代码就绪 |

### 2.3 实际部署命令

**单体模式（当前运行）**：
```bash
cd RAG-BACKEND
docker compose up -d --build rag-server
# SPRING_PROFILES_ACTIVE=prod → 所有Controller加载
```

**微服务模式（需16GB+内存）**：
```bash
# 每个微服务共享 rag-server:latest 镜像，不同 Profile
docker run -d --name rag-auth --network rag-network -p 8081:8080 \
  -e SPRING_PROFILES_ACTIVE=auth [其他env...] rag-server:latest
# 同理启动 rag-kb, rag-doc, rag-qa, rag-config
```

### 2.4 关键经验

1. **Profile 必须匹配运行环境**：容器 `SPRING_PROFILES_ACTIVE=prod`，则 `@Profile` 必须包含 `"prod"`
2. **role_permissions 数据保护**：重建容器时确保权限数据不丢失
3. **源码双份维护**：`src/`（单体）+ `rag-common/src/`（微服务共享层）
4. **单体优先**：开发测试用单体，生产扩展用微服务

## 5. 完整部署（含 Gateway + 监控）

### 4.1 启动核心服务

```bash
cd RAG-BACKEND
docker compose up -d
# 启动: mysql, redis, kafka, minio, etcd, milvus, nacos, rag-python, rag-server
```

### 4.2 启动 Gateway

```bash
docker run -d --name rag-gateway \
  --network rag-network \
  -p 8088:8080 \
  -e JWT_SECRET=your-256-bit-secret-key-change-in-production \
  -e REDIS_HOST=redis \
  -e REDIS_PASSWORD=redis123 \
  rag-gateway:latest
```

### 4.3 启动监控栈

```bash
docker compose -f docker-compose-monitoring.yml up -d
# 启动: loki, prometheus, grafana
```

### 4.4 启动微服务（内存充足时）

```bash
# 每个微服务独立启动（共享 rag-server 镜像，不同 Profile）
for svc in "rag-auth:8081:auth" "rag-kb:8082:kb" "rag-doc:8083:doc" "rag-qa:8084:qa" "rag-config:8085:config"; do
  IFS=':' read -r name port profile <<< "$svc"
  docker run -d --name $name --network rag-network -p $port:$port \
    -e "SPRING_PROFILES_ACTIVE=$profile" \
    -e MYSQL_HOST=mysql -e MYSQL_PASSWORD=root123 \
    -e REDIS_HOST=redis -e REDIS_PASSWORD=redis123 \
    -e KAFKA_BOOTSTRAP_SERVERS=kafka:9092 \
    -e "MINIO_ENDPOINT=http://minio:9000" \
    -e MINIO_ACCESS_KEY=minioadmin -e MINIO_SECRET_KEY=minioadmin123 \
    -e JWT_SECRET=your-256-bit-secret-key-change-in-production \
    -e NACOS_SERVER_ADDR=nacos:8848 \
    rag-server:latest
done
```

## 10. 常见问题

**Q: Gateway 启动后 API 返回 401**
A: 检查 JWT_SECRET 与 rag-server 一致

**Q: 微服务容器 Exited (1)**
A: 内存不足，减少并发启动数量，逐个启动

**Q: Nacos 服务列表为空**
A: 等待服务心跳注册（首次约 30s），检查 NACOS_SERVER_ADDR 配置

**Q: Kafka 连接失败**
A: 确认 KRaft 模式配置正确，检查 KAFKA_ADVERTISED_LISTENERS
